# Decisions

Lightweight ADR log. Every decision that would be expensive to silently reverse gets an entry here, in order, never edited after the fact — a later decision that changes an earlier one adds a new entry and marks the old one superseded. This exists because the prior attempt at this product (`pikorua-luxe-compare`) pivoted infrastructure (Supabase → self-hosted Postgres) with no decision record, discovered only via a panicked migration 4 days before development stalled. See `docs/postmortem-2026-08.md` if/when that debrief is written up in full.

Format: **Date — Decision.** Context. Why. Alternatives considered.

## Decisions taken by Bhavarth

**2026-08-31 — Rebuild from scratch; old project (`pikorua-luxe-compare`) is requirements/lessons only, not a template.**
Context: prior attempt stalled after ~5.5 weeks. Why: its own final handoff note recommended exactly this; root failure was two live schemas of the same entity coexisting and diverging, not a fixable code issue. Alternatives: fork and refactor — rejected, the dual-schema wound was structural.

**2026-08-31 — Full three-role platform (buyer / developer / admin), sequenced buyer-first.**
Buyer experience + admin-run OCR ingestion ship first; developer self-serve submission portal ships later. Why: brochures + GujRERA are the only data sources available, so an ingestion pipeline is required from day one regardless — but a developer-facing UI for it is not required to launch to buyers.

**2026-08-31 — Self-hosted PostgreSQL, own VM/Docker (not managed/hosted DB).**
Matches the old project's own concluded-correct infra choice, made independent of this decision.

**2026-08-31 — Next.js (App Router) over TanStack Start for the frontend.**
Why: SEO/ISR maturity matters for organic search on property pages; Next.js has far greater representation in AI-agent training data, reducing hallucination risk with two AI coding agents (Claude Code + Codex) writing this codebase in parallel. Drizzle ORM, Better Auth, and Google Cloud Storage for media all carried forward unchanged from the old stack.

**2026-08-31 — OCR ingestion targets a predefined, versioned field schema; anything outside it is discarded, not stockpiled.**
Reacting directly to the old project's outcome: 824 fields flagged for review against only 315 auto-accepted. Enforced in schema via `property_schema_fields` (see `docs/schema/schema.v1.md`) — the OCR pipeline extracts only what's listed there.

**2026-08-31 — GujRERA data is fetched via a structured scrape/fetch job and used only as an independent cross-check against brochure OCR — never blanket "verified" badging.**
A `rera_fetch_jobs` row that disagrees with a brochure becomes a new `property_submissions` row (source = `rera_scrape`), subject to the same admin approval as any other change — RERA fetches never write live data directly.

**2026-08-31 — Geography fixed to Ahmedabad/Gujarat only; target buyers broadened from ultra-luxury-only to the full regular-to-ultra-luxury spectrum; property types fixed to Apartment / Bungalow / Plot (lookup table, softly extensible).**
Location is still modeled as structured fields (city, locality, lat/long, pincode) rather than free text, to support map/locality search later without a schema change now.

**2026-08-31 — Exact unit prices are never shown in the app. Price data exists only to bucket properties against a buyer's stated budget during discovery/comparison matching.**
On the property detail page specifically, the default is **zero price shown at all**, until the buyer submits an enquiry — stricter than "show a bucket." Commercial data (`unit_price_history`) lives in a separate `private` Postgres schema, RLS enabled with zero policies (deny-by-default, service-role only), reusing the old project's validated isolation pattern. Buyer-facing bucket matching reads only a derived `private.unit_current_bucket` view via a single service-role code path — no other code path may query `private`. Default may change later per explicit product decision, not silently.

**2026-08-31 — Developer portal and admin/verification portal are two separate, distinctly-permissioned interfaces, not one shell gated by role.**
Context: the Stitch UI export's "Editorial Desk" shell conflated developer-portfolio-analytics and admin-OCR-verification into one sidebar; on inspection this was generation noise (Stitch reusing a convenient shell across unrelated concepts), not an intentional merged design. Decided to build them as genuinely separate surfaces with separate permission models, matching the draft→submit→approve→publish trust boundary where a developer must never have review/approve capability over their own submissions.

**2026-08-31 — Design system: "Soft Daylight" v2 (Cormorant Garamond + Plus Jakarta Sans, Soft Gold reserved for Verified badges) is canonical.**
Two competing token specs existed in the Stitch export; v2 was chosen because the actual reviewed screens (gold-toned RERA Verified badge) matched it, and it includes the more developed component set (PropScoreDial, evidence-viewer treatment). Full tokens: `docs/design/design-tokens.md`.

**2026-08-31 — One canonical write path into live catalog tables: the `property_submissions` publish transaction. No migration/seed/backfill script may write to `properties` or its child tables directly.**
This is the direct fix for the old project's root failure: a backfill script called the "V2 publish" path directly, bypassing developer review and admin approval entirely. Schema-enforced via `property_revisions` (a snapshot is written every time, in the same transaction, as an audit trail); process-enforced via `AGENTS.md` for any human or AI contributor.

**2026-08-31 — Original whiteboard schema image included a `Reviews` entity and an unlabeled RERA-extract fields block; neither made it into `schema.v1.md`'s first pass, and their resolution wasn't written down anywhere. Re-derived from a re-shared photo of the whiteboard and closed out here.**
Context: this is a direct instance of the failure mode `AGENTS.md` line 20 exists to prevent — the earlier resolution of these fields happened in conversation and was never given a dated entry, so it was lost to context compaction and had to be re-derived from the original whiteboard photo. Resolutions, applied to `docs/schema/schema.v1.md`:

- `reviews` table added (property-level, not unit-variant-level, matching the whiteboard exactly: `id, property_id, user_id, rating, remarks`) — extended with verification fields (`verification_status`, `verification_document_id` reusing `source_documents`, `verified_by`, `verified_at`) rather than shipped as a bare star-rating table, per the explicit decision to build in verification from day one rather than defer it.
- The whiteboard's unlabeled blue-ink block (`rera_id?, progress?, project_land_area, carpet_area_range, amenities{}, builder_details{}, total_units, total_towers, project_status`) is RERA-extract data at the project level. `total_units`/`total_towers`/`possession_date` were already columns on `properties`; `amenities{}` and `builder_details{}` are already covered by `property_amenities` and `developers` respectively (not duplicated); `project_status` maps to the existing `possession_status` enum. The two genuinely new facts — `project_land_area` and `carpet_area_range` — plus `progress` (construction completion %) are added as new nullable `properties` columns (`rera_project_land_area_sqft`, `rera_carpet_area_range_min_sqft`/`_max_sqft`, `rera_construction_progress_percent`), populated only when `rera_registered` is true, consistent with whiteboard Q1's "RERA fields live directly on `properties`" resolution.
- The whiteboard's `Configurations` entity named layout forms (Penthouse, Duplex) alongside N-BHK counts. `bhk_types` stays bedroom-count-only; a new `layout_types` lookup was added instead of overloading `bhk_types`, and `unit_variants` now carries both `bhk_type_id` and `layout_type_id` independently (a unit can be a 3BHK duplex, for example).

Why this entry is longer than usual: it exists specifically to make sure this exact loss doesn't happen again — anyone re-deriving these fields from a whiteboard photo in the future should find them here first.

**2026-09-01 — Private-schema access uses separate PostgreSQL app and service roles.**
Context: PostgreSQL table owners bypass row-level security by default. The initial local `DATABASE_URL` used the Docker bootstrap/owner role, so RLS with zero policies would not actually prevent regular application code from reading exact prices. Resolution: the normal application connection is `propcompare_app`, which receives public-schema privileges and no `private` schema usage; migrations use the non-runtime `propcompare` admin role; the future discovery/comparison service alone uses `propcompare_service`, a narrowly reserved `BYPASSRLS` role. `private` tables have RLS enabled and forced with zero policies. Why: preserves the already-decided rule that exact prices never reach ordinary app code while using PostgreSQL's own enforcement rather than a convention. Alternatives: retain one owner connection and rely on code discipline — rejected because it defeats the stated RLS boundary.

**2026-09-02 — OCR page routing cannot rely on text-layer/keyword inspection; it requires a vision-capable model actually reading each page.**
Context: `docs/tasklists/2026-09-01-phase-2a-ocr-routing-foundation.md` assumed "cheap text-layer inspection may suggest scopes" as the pre-human-confirmation routing step. Empirical test against 3 real brochures (`docs/tasklists/2026-09-02-ocr-provider-selection.md`) found zero pages, across all 3 brochures, with any area/sqft text in the extractable text layer — floor plans and site plans in these brochures are raster images with no underlying text at all. A pdfjs keyword-scored router built on this assumption reliably picked marketing/lifestyle pages instead and missed every floor plan. Resolution: whatever generates routing-manifest candidates must use a model that reads page images/native PDF vision, not text extraction — text-layer inspection may still help for text-heavy categories (specifications, RERA/legal) but cannot be the sole mechanism. Still human-confirmed either way, per the original decision. Alternatives: keep tuning the keyword list — rejected, the data these keywords target has no text-layer presence to match against, no list fixes that.

**2026-09-01 — Buyer budget matching uses an inclusive ±20% expansion of the buyer's stated range.**

**2026-09-01 — Brochure OCR is routed by a human-confirmed, versioned page manifest before paid extraction.**
Context: brochure page boundaries are not unit-variant boundaries. A penthouse or duplex may span lower-floor, upper-floor, and terrace pages, while a brochure may also contain many pages irrelevant to the approved extraction contract. Resolution: cheap PDF text-layer inspection may suggest page scopes, but an uploader must confirm the routing manifest before extraction. A confirmed unit-variant scope contains one proposed variant identity and one or more ordered pages; the OCR adapter must return at most one variant candidate for that scope. Multiple pages therefore remain evidence for one proposed canonical `unit_variants` item rather than becoming separate variants. The routing manifest is stored with a pipeline and field-contract version on the OCR attempt and becomes immutable once queued. It is processing metadata only and never writes to the live catalog. Why: this reduces paid page processing and prevents document layout from silently defining catalog identity. Alternatives: OCR the entire brochure and infer grouping afterward, or treat every floor-plan page as a separate variant — rejected as costly and structurally unreliable.

**2026-09-01 — Historical OCR JSON is evaluation evidence only; every selected brochure is reprocessed through the new pipeline.**
Context: the existing property JSON files were produced by the retired pipeline and may contain exactly the grouping and normalization errors the new flow is intended to prevent. Resolution: historical output may be normalized into a derived comparison report against a new run, but it cannot create `property_submissions`, `property_submission_fields`, or live catalog data. **2026-09-01 — Submission-field provenance is one-to-many evidence; OCR attempt status belongs to attempt rows, not source documents.**
Context: `property_submission_fields.source_page` can cite only one page, but one field—especially the `unit_variants` array—may depend on several brochure pages. `source_documents.ocr_status` also cannot truthfully represent retries or pipeline-version comparisons. Why: provenance and retry history become reproducible without duplicating a property or variant entity. Alternative: place page arrays inside field values or keep both document and attempt statuses — rejected because those approaches mix provenance into canonical values or create two live statuses for one process.

**2026-09-01 — Builder profiles exist independently from builder staff accounts; admin-run ingestion precedes self-serve onboarding.**
Context: the initial catalog will be curated by admins from builder brochures, including builders that have no account on PropCompare. Later, builders should upload, map pages, review their own OCR draft, and submit it for independent admin approval. Initially an owner admin may create, review, approve, and publish an admin-run submission, with all actions audited. Why: the initial data-collection workflow works without fake accounts, while the future portal has a clear ownership boundary. Alternatives: require every builder to sign up before curation, or use OCR spelling as a developer identity — rejected because both block reliable initial ingestion.

**2026-09-01 — Published-property updates are additive patches; omission never deletes brochure facts.**
Context: a later brochure often contains only a subset of a property’s facts, and OCR absence means “not found in this selected evidence,” not “not offered” or “no longer exists.” Resolution: on an existing property, a submission updates only the canonical fields it explicitly carries. Present amenities and specifications add or update evidence-backed facts; omitted ones stay unchanged. Present unit variants upsert only by exact reviewed `variant_name`; a new name adds a variant. Automatic variant deletion, renaming, or fuzzy matching is forbidden in v1 and requires an explicit future review action. A new property receives `not_stated` rows for unmentioned controlled catalog items, while explicitly extracted items become `available`; automatic negative claims are never inferred. Why: preserves catalog integrity while allowing new brochures to improve it incrementally. Alternatives: treat every brochure as a complete replacement or infer removals from missing OCR — rejected because either can silently erase correct published data.

**2026-09-01 — Submission review permissions and slug generation are fixed for Phase 2A.**

**2026-09-02 — Per-unit segmentation of a floor-plan page belongs to the extraction step, not the page-routing step.**
Context: `docs/tasklists/2026-09-02-ocr-provider-selection.md`'s page router first tried to distinguish "single sellable unit" floor-plan pages from "multi-unit floor plate" pages, and to group a unit's own multi-page pairs (duplex/penthouse lower+upper) under one label at routing time. Both failed in practice: (1) a floor plate showing multiple units on one drawing (e.g. two mirrored flats, each fully dimensioned) routinely carries complete, usable per-unit data — "multiple units on a page" does not mean "no unit data," so splitting floor-plan pages into two categories on that basis was a false distinction confirmed against a real brochure page (Kimana Towers, pg 8: two fully-dimensioned mirrored units, 301/302, on one drawing); (2) grouping a unit's pages under one label requires closely reading the actual drawings to tell which walls/dimensions belong to which unit — a cheap router classifying small page excerpts can't do this reliably, and demonstrably fragmented one physical duplex into two different labels when its two pages landed in different classification batches. Resolution: page routing's only job is recall — flag every page with floor/site-plan content for human-confirmed inclusion, using one `floor_plan` category regardless of how many units are drawn on a page. Identifying distinct units on a page, and merging a unit's pages that span more than one page, is the extraction model's job, done against the full confirmed page range with an explicit instruction covering both cases. Verified working: Claude Sonnet 5, given only the confirmed non-marketing pages of the 360 brochure, produced the exact 6 unit variants a human had already confirmed, correctly merging each duplex/penthouse's lower+upper pages on its own. Why: the model that already has to read a page closely for extraction is the same model positioned to correctly attribute dimensions to units on that page; asking a coarse router to pre-solve that is asking the wrong stage to do a job it structurally can't do well. Alternatives: keep the single-unit/multi-unit category split — rejected, provably wrong; keep routing-side unit-variant grouping with a chunk-boundary reconciliation pass — worked but only patches a problem this resolution removes at the root, and added cost/complexity for no accuracy gain over doing it once at extraction time.

**2026-09-02 — OCR extraction provider is Claude Sonnet 5 (`claude-sonnet-5`), called via OpenRouter with native PDF ingestion.**
Context: `docs/tasklists/2026-09-02-ocr-provider-selection.md` ran the same extraction prompt against four models — Claude Sonnet 5, Claude Opus 5, OpenAI GPT-5.6 Sol, and GPT-5.6 Terra — over three real brochures (360, Adani Amaris, The Kimana Towers), using OpenRouter's `file-parser` plugin with `pdf.engine: "native"` so each model used its own native PDF/vision ingestion rather than OpenRouter's default OCR preprocessing. Measured total cost per brochure (sum of all pages/scopes sent): Sonnet 5 $0.253, Opus 5 $0.561, GPT-5.6 Sol $0.632, GPT-5.6 Terra $0.654 — Sonnet was cheapest of the four despite comparable or higher OpenAI list pricing, because Claude's native PDF engine consumed 1.5x-3.9x fewer prompt tokens per page for the same PDF than GPT-5.6's. Structural validity (well-formed JSON matching the field contract) was equivalent across models except one Kimana run where Sonnet hit its completion-token ceiling on an oversized single-pass request (`finish_reason=length`); the tasklist's later batch-by-scope requests fixed this and priced even lower per brochure. Resolution: production OCR extraction calls Claude Sonnet 5 through OpenRouter, using the `file-parser`/native-PDF-engine plugin configuration validated in the bake-off, with per-scope (not whole-brochure) requests to bound completion-token risk. Provider choice is tracked here per `docs/roadmap.md`'s Phase 2A bullet. Why: lowest measured cost among tested models for equivalent structural output, validated against the working page-routing/extraction split recorded above. Human spot-checks of field-level (not just structural) accuracy on the Adani Amaris and Kimana Towers brochures remain outstanding and are carried into the provider-integration tasklist rather than blocking this provider selection, since the 360 brochure's unit-variant output was independently verified against a human-confirmed baseline. Alternatives: GPT-5.6 (either tier) — rejected, no accuracy advantage found and consistently more expensive; Claude Opus 5 — rejected, no accuracy advantage found over Sonnet in this bake-off and roughly 2.2x the cost.

**2026-09-02 — Buyer read routes are request-time handlers whose caching is expressed as HTTP `Cache-Control` for a shared cache; Next.js-level ISR is not used on the JSON routes.**
Context: SEO/ISR maturity was an explicit reason for choosing Next.js (2026-08-31), and Phase 2B step 3 could not ship two public read routes without deciding what caches them. Three things constrained the choice, each checked against the bundled Next 16 docs rather than assumed: `cacheComponents` is not enabled, so `GET` Route Handlers already run at request time by default; `dynamic = "force-static"` is unavailable to the listing route in principle, because a force-static handler cannot read `request.nextUrl.searchParams` and that route is defined entirely by its query parameters; and prerendering the dossier route with `generateStaticParams` would require Postgres reachable at build time. Resolution: neither route exports a route segment config. Successful listing responses carry `public, s-maxage=60, stale-while-revalidate=300`; successful dossier responses carry `public, s-maxage=300, stale-while-revalidate=3600`; every error response carries `no-store`. The directives are shared-cache only — no browser `max-age` — so a CDN or reverse proxy absorbs repeated load while a buyer changing a filter still gets a fresh response rather than one their own browser is holding. The listing window is short because it is filtered, paginated, and should surface a new property quickly; a dossier is a stable per-slug document and tolerates longer. Errors are never cached so that a `404` cannot outlive the publish that resolves it. Why: this is portable across self-hosted and managed deployment, independent of Next's internal cache, and leaves the SEO decision where it actually belongs — page-level ISR on the dossier _page_, decided in step 6. Alternatives: `no-store` everywhere and defer — rejected, it makes every buyer request a database hit for no gain; prerendering the dossier JSON with `generateStaticParams` + `revalidate` — rejected, it couples the build to a reachable database and delays a re-publish behind a revalidation window, for a route no crawler reads.

**2026-09-02 — The `code` field of the API error envelope is a machine-readable slug, not the HTTP status restated; malformed input is rejected rather than repaired.**
Context: `api-spec.v1.md` defined the envelope as `{ "error": { "code", "message" } }` and then said "expected codes include `400`, `401`, ..." — leaving `code` genuinely ambiguous between a status restatement and a failure-class name. Resolution: `code` names the failure class (`unknown_query_parameter`, `invalid_query_parameter`, `property_not_found`, `internal_error`); the HTTP status carries the status, and `message` is developer-facing prose naming the offending parameter. **2026-09-18 — Buyer-facing media is served through `GET /api/v1/media/{id}`, a redirect route that generates a fresh GCS V4 signed read URL per request; the signed URL is never baked into ISR-cached HTML. Supersedes the signed-URL rejection in the 2026-09-07 dossier-media-gate entry.**
Context: that 2026-09-07 entry rejected signed URLs specifically because "expiring URLs fight the ISR-cached HTML" the dossier page (`revalidate = 3600`, one hour) uses — a signed URL baked directly into the page's cached markup could expire before the next regeneration, serving a broken image for up to the remainder of the window (longer under `stale-while-revalidate` lag). Resolution (user sign-off, after the tradeoff was raised directly): keep the _indirection_ the 2026-09-07 entry favored in a proxy route, but implement it as a redirect to a signed URL rather than streaming bytes through the route itself. Cached HTML references the stable `/api/v1/media/{id}` path on our own domain — that reference never goes stale, since it names no expiring credential — and each request to it resolves `property_media.gcs_path` and calls the storage adapter's new `getSignedReadUrl(path, { expiresInSeconds })` (`src/lib/storage/adapter.ts`, implemented in `gcs-adapter.ts` via `File.getSignedUrl({ action: "read", version: "v4", expires })`), then issues a `302` to it. The signed URL's TTL is short (a few minutes) — it only needs to outlive the moment between the redirect and the browser following it, not the page's cache window, because it is generated live at request time rather than at page-render time. Why this doesn't cost a network round trip per image: V4 signing computes the signature locally from the service account's private key: no call to Google is made to produce the URL, only to serve the eventual `GET` once the browser follows the redirect. Why not a full proxy that streams the file's bytes itself (the option the 2026-09-07 entry called "the strongest candidate"): it remains available later if ever needed (e.g. to enforce access control on private media), but buyer-facing property photos are meant to be public once published, so there is no access decision this route needs to make — redirecting to GCS directly is simpler and avoids doubling this server's egress bandwidth for every image on every page view. Why not a public bucket: unchanged from 2026-09-07 — `property_media.media_type` includes `brochure_pdf`, and a hard separation between source documents and buyer media is still an open question this doesn't need to resolve, since nothing here makes any bucket contents public. `docs/api/api-spec.v1.md` documents the route once implemented. Not yet done: actually wiring `PropertyCard`/the dossier's media rendering to emit `<img src="/api/v1/media/{id}">` instead of the deliberate placeholder frame from the 2026-09-07 entry — that stays as its own follow-up, since it touches buyer-facing components with tests that currently assert the placeholder on purpose, and there is still no real media data to render against (the catalog is empty, per the 2026-09-18 status-audit entry above). Alternatives: a long-TTL signed URL baked directly into the cached page — rejected, it works only as long as the TTL is kept safely ahead of the revalidate window and any `stale-while-revalidate` lag, which is a fragile invariant to maintain correctly forever versus a redirect route that has no such constraint at all; a full byte-streaming proxy — deferred, not rejected, since it may become the right choice if brochure-vs-media separation or access control needs change later, and the interface (`StorageAdapter`) does not foreclose adding it.

**2026-09-21 — Brochure extraction runs in a durable in-server worker that the queue confirmation feeds; Brevo is the email provider.**
Owner asked for the real consumer, not a script. Choices made while building it:

- **The queue is the database.** A queued `ocr_extraction_jobs` row is the work item, so a restart loses nothing. Claiming is the existing conditional `queued → processing` update, so any number of workers can run and only one gets a job. No schema change and no new queue technology.
- **Where it runs.** `src/instrumentation.ts` starts one polling loop per server process (guarded against dev reloads, skipped under test and when `OCR_WORKER_ENABLED=false`), so `bun run dev` and `bun run start` are enough. `bun run ocr:worker` runs the same loop alone for a host that separates web and worker. Alternatives rejected: work inside the queue request (extraction takes minutes and would be lost on any timeout or restart); a serverless queue (no hosting decision yet, and the database already is a queue).
- **Only explicit work.** The worker picks up only jobs an admin queued through the separate confirmation. It never runs on upload or categorize.
- **Crash recovery.** A running job refreshes `updated_at` every minute; one silent for ten minutes (`OCR_WORKER_LEASE_MS`) is failed as `worker_interrupted`, visible in the UI and retryable. A job that cannot even start (missing key, unreadable routing) is failed rather than left queued.
- **Retry is an admin choice, and paid.** A failed attempt can be re-queued (a second paid run, so its own confirmation with no price) or reopened as a draft to change the pages (needed after `output_length`, where the same pages would fail again). Only a failed attempt can move, by a conditional update.
- **Failure text.** Screens show a plain-language message chosen from the error code, never the stored provider message, which can quote a response.
- **Ledger gap closed.** When a run fails part-way, requests already billed (scopes that succeeded, and the one whose reply was unusable) are recorded. Kept beside the error, not on it, so no error type changes shape.
- **Test seam.** `OPENROUTER_OCR_ENDPOINT` points extraction at a stand-in provider for end-to-end checks; unset in production.
- **Email: Brevo** (owner, 2026-09-21). `src/lib/email/` follows the storage and OCR adapter pattern. Invite links are emailed when `BREVO_API_KEY` and `BREVO_SENDER_EMAIL` are set and always still shown on screen, so a missing or failing provider never blocks an invitation; only failure codes are logged, never addresses or links. The sender domain must be verified in Brevo before this is trusted in production (`docs/production-readiness.md`).

**2026-09-20 — Units are exact: feet and square feet only, converted in code once from a printed unit, never assumed.**
Owner rule, non-negotiable, saved to project memory: a wrong unit is never acceptable. Trigger: Kimana Towers' room dimensions were stored as feet but the brochure printed metres (a 4.36 by 7 "ft" bedroom; the plans say "1.15 M HT. PARAPET", "1.53 M WIDE PASSAGE", "LIFT 2.15X1.82"). Root cause: the extraction prompt named the fields `lengthFt`, `widthFt` and `areaSqft` and told the model to copy printed numbers, so the model never reported a unit and nothing converted; `property.plot_area_sqft` even asked the model to "normalize to square feet" itself. **The fix is structural.** (1) `src/lib/units/measurements.ts` reads a printed measurement with its unit and converts exactly (1 ft = 0.3048 m; sq m, sq yd, guntha, acre, feet-and-inches, mm, cm, in); a number with no unit is refused, never assumed; an unrecognised unit is refused, never replaced by feet; a length unit cannot stand for an area. (2) The model now returns what is printed plus the unit it found (with the number, or once for the plan as `lengthUnit` / `areaUnit` / `unit`, or null), and never converts. (3) `convertProviderDetails` in `src/lib/ocr/adapter.ts` is the **one** place a raw reading becomes canonical (`lengthFt`, `widthFt`, `areaSqft`); measurements with no printed unit are left out and logged, never guessed. (4) **Converted exactly once:** the model-facing shape (`length`, `area`, `unit`) and the canonical shape (`lengthFt`, `areaSqft`) are mutually incompatible, so canonical data handed to the converter is ignored and raw data handed to the canonical validator is rejected; tests replay the same saved answer repeatedly and re-validate the canonical result to prove nothing converts twice. (5) `dimensionsWarning` warns in the admin (the Rooms tab and the unit-type summary) when a unit type's largest room is under 60 sq ft or a side exceeds 120 ft, the signature of metres, inches or millimetres stored as feet; it warns and never blocks. (6) Found on the way: the extraction validator had no case for the `positive_number` data type, so `property.plot_area_sqft` could never be extracted (silently dropped as unsupported); fixed. RERA reports square metres; the panel converts for display with the same constant. **Corrected on Kimana:** `src/db/correct-dimension-units.ts` converted all 171 rooms and balconies across its 6 unit types from metres to feet through an edit submission and the publish path (dry run by default; it refuses to run twice because it only converts when the stored sizes still look like the wrong unit, which was proved by running it again). **2026-09-20 — The scheduled RERA refresh: due from what the record says, drafts never live writes, and off until switched on.**
(1) **Due rule.** A published property whose RERA number a registered regulator issues is due when its last good record does not show a filing for the latest calendar quarter whose filing window (1–7 of the next month, plus a day of grace) has closed. It is then re-checked weekly until a filing shows, or after a day, doubling per consecutive failure and capped at a week, when a check failed. Decided from the record and not from the calendar alone because late filers pay a daily fee and deadlines have been extended by order. Completed projects that stop filing are re-checked weekly indefinitely; that is one request each and was accepted over guessing when a project is "finished". (2) **A difference becomes a draft, never a live write.** One `rera_scrape` edit draft is opened for the property, its values saved as `needs_review` (an admin's own "use RERA values" stays `confirmed`, because a person chose it); the submission has no author. None is opened when nothing differs, when an edit is already open (the RERA panel shows the difference in that edit), or when the newest scheduled proposal was rejected and this one is identical, so a rejected change is not raised every quarter; a changed RERA value is a new proposal. (3) **No schema change and no lease column.** A worker locks the property row (`FOR UPDATE SKIP LOCKED`) and inserts its `running` job in the same transaction; a job left running for 15 minutes is failed as interrupted. Four simultaneous claims are tested to yield one. (4) **Off by default**, unlike the extraction worker: it reads a public site on its own, so it needs `RERA_WORKER_ENABLED=true` (or `bun run rera:worker`), and requests are spaced (15 s). The owner reports GujRERA shows no blocker; its terms were not independently reviewed, which is listed in `docs/production-readiness.md` with failure alerting. (5) **Revision history** on the submission screen reads `property_revisions`: when each edit went live and what it changed, as was and now for single values, "changed" for sets. **For the owner's review:** the scheduler creates drafts in the queue by itself; it changes no publish logic. Root cause: `postgres` (the driver, used via `drizzle-orm/postgres-js`) auto-parses `jsonb` into native JS values before Drizzle ever sees them, but Drizzle's own `jsonb()` column unconditionally `JSON.parse`s anything it receives that is `typeof "string"` — correct for drivers that hand back raw text, wrong for one that has already parsed it. For an object or array this second parse is a no-op. For a JSON **string whose own characters are also valid bare JSON** — a six-digit PIN code, `"true"`, `"null"` — it silently changes type (the pincode read back as the number `382481`). No other `jsonb` column in this schema (`dimensions`, `fetched_payload`, `routing_manifest`, `snapshot`, and so on) stores a bare scalar; `property_submission_fields.value` is the only one, and pincode is the first contract field whose legitimate value is always pure digits, which is why this had never been seen before. **Fix:** `src/db/jsonb-types.ts` tells the `postgres` client to hand `jsonb` (oid 3802) back as raw text, so Drizzle's parse is the only one; applied to every production client (`src/db/index.ts`, `src/db/service.ts`, `src/db/seed-private.ts`). Verified: a raw-driver probe confirmed the corruption and the fix; the full suite (129 files, 1542 tests, including integration tests against the real database, several of which write and read `jsonb` object/array columns) stayed green before and after, evidence the change is behaviourally invisible except for the bug it fixes.

**Applied to the three live properties.** Kimana, Amaris and Maruti 360 were each taken through a real edit ("Edit this property", RERA re-fetch, "Use RERA values", publish) so the fix is not just code: all three now read `rera_registered = true` and carry RERA's project land area; Amaris also gained its pincode (Kimana's and Maruti 360's RERA records state none, an honest gap, not a bug). Launch date stays "not stated" on all three: RERA does not report it, and no brochure has been re-run since the field became writable.

**2026-09-23 — Floor-plan extraction bounds its output by discovered unit, not by hoping a scope's page count stays small enough. Two provider calls per floor-plans scope now, both reading the full page range, neither changing the routing contract.**

Context: a real extraction (Godrej Properties, job `04098e3b-617c-4578-974b-3bf4220c89ac`) failed `output_length` on a 9-page `floor-plans` scope. The 2026-09-02 decision already bounded risk by sending one provider request per _scope_ instead of the whole brochure, but every scope call shares one fixed `max_tokens` (`DEFAULT_MAX_COMPLETION_TOKENS`, 32,000) regardless of page or unit count, and the floor-plans prompt asks for full room-by-room detail for _every_ discovered unit in _one_ response — so output size scales with a brochure's own complexity, not something a page-count threshold can safely predict (Maruti 360 succeeded with 10 pages; this brochure failed with 9).

**Why not a blind page-count split.** `routing.ts` forbids more than one `floor_plans` scope in a manifest, on purpose: a duplex or penthouse's lower and upper levels must be read _together_ for the model to merge them into one unit rather than fragmenting it into two (the 2026-09-02 decision above this one, the Kimana duplex-fragmentation bug it fixed). The router's own per-page captions can't substitute for this either — the router captions each page independently, one at a time, so it structurally cannot know two pages belong to the same unit; the 2026-09-02 decision already tested exactly this idea at the routing stage and rejected it for that reason ("a cheap router classifying small page excerpts can't do this reliably... demonstrably fragmented one physical duplex into two different labels").

**Resolution: two passes, both reading the full page range together.** (1) A cheap discovery call over all of a `floor_plans` scope's pages, asking only which pages belong to which unit — no room detail, so its output stays small regardless of page count and never approaches the ceiling. (2) One bounded extraction call per discovered unit, reusing the _existing_ `unit_variant` scope kind's prompt and parsing exactly as built — each call's output is bounded by one unit's own detail, not the whole scope's. A page discovery does not assign to any unit is never silently dropped: it becomes its own small fallback `floor_plans`-kind scope (the original, unchanged discover-and-extract-together handling), so nothing is lost to a discovery miss.

This needed no schema or routing-contract change. The human-confirmed, stored routing manifest still carries exactly one `floor_plans` scope — the split happens entirely inside `createOpenRouterOcrAdapter`'s handling of that one scope, which builds an internal "effective manifest" (the confirmed one, each `floor_plans` scope expanded into synthetic `unit_variant` scopes) that only the adapter's own extraction pass and persistence ever see. `routing.ts`'s "one floor-plans scope" check is never run against it, because it is constructed directly in memory rather than round-tripped through the parser that enforces that rule.

**A real bug found and fixed on the way, not incidental:** `OcrProviderExtractionResult` gained `effectiveManifest`, and `src/lib/ocr/ingestion.ts`'s persistence path (`persistOcrExtractionResult`, called from both `executeOcrExtractionJob` and `retryOcrExtractionPersistence`) now resolves a unit variant's `scopeKey` against it instead of re-parsing the confirmed manifest fresh from the database. Without this, every floor-plan-discovered unit variant would have silently vanished at persistence: `buildSubmissionFieldCandidates` looks up candidates by the confirmed manifest's own scope keys, and a synthetic key like `floor-plans:unit:0` does not exist there. Caught before it shipped by tracing every consumer of `scopeKey`, not by a failing test — worth noting because a persistence-time silent drop is exactly the kind of failure this project's evidence/field-contract discipline exists to prevent, and it would have looked like a successful extraction with quietly incomplete data.

**Verified:** typecheck, lint, format:check, and the full suite (133 files, 1589 tests) — `adapter-resilience.test.ts` and `ocr.test.ts`'s floor-plans coverage updated for the two-call shape (a discovery mock plus a per-unit mock in place of one multi-variant mock), preserving natural document order (discovery for a `floor_plans` scope runs inline where that scope sits, not as a separate up-front pass over every scope) so checkpoint order and partial-usage billing on a mid-run failure stay exactly as predictable as before. Not yet done: re-routing and re-queueing the actual failed Godrej job through the fixed pipeline is a paid provider call and is held for the owner's go-ahead, per the standing "confirm before any paid run" rule.

Tasklist: `docs/tasklists/2026-09-23-floor-plan-unit-discovery.md`. Alternatives considered: a page-count threshold that only splits very large scopes — rejected, page count doesn't predict output size reliably enough to trust (see Maruti 360 vs. this brochure above), and a scope just under the threshold would still be able to fail; reusing the page-router's existing per-page captions to group units — rejected, the exact idea the 2026-09-02 decision already tried and found unreliable, for a reason (independent per-page captioning) that persists regardless of which model or image quality the router uses.

The 2026-09-02 Kimana Towers incident (same file, above) already diagnosed and fixed this exact pattern once — Sonnet transcribing mirrored units and repeated floor-range plans as separate ~30-room variants, roughly doubling cost and risking `output_length` — with an explicit prompt rule ("rule 10": mirrored/repeated layouts collapse into one variant, named to cover every unit/floor it represents). That fix lived only in a one-off eval script (`docs/tasklists/2026-09-02-ocr-provider-selection.md`), never the production prompt. The 2026-09-20 decision that first added floor-plan discovery-at-extraction-time didn't carry it forward, and this week's discovery prompt (`createFloorPlanDiscoveryPrompt`) went further and told the model the opposite — its own rule 3 said a page with several mirrored units should list them as separate units. Two rewrites of this prompt, two silent drops of a rule that had already been paid for once. Godrej's 17 discovered units (four "Flat No. 101–104," four "Flat No. 201–204," repeated across explicitly-labelled floor tiers) are exactly the shape rule 10 was written to collapse.

**Fix, three parts, same commit as this entry:**

1. **Reinstated the merge rule** (`MIRRORED_UNIT_MERGE_RULE` in `adapter.ts`, used by both `createFloorPlanDiscoveryPrompt` and the `floor_plans` scope kind's extraction prompt), with a comment citing this history explicitly so a third rewrite has to read past it to drop the rule again. This should cut Godrej's 17 discovered units down to however many are genuinely distinct — the primary lever, since it reduces both the fan-out count and the amount transcribed per call.
2. **Discovery moved off Sonnet onto a cheap model** (`google/gemini-2.5-flash`, `DEFAULT_FLOOR_PLAN_DISCOVERY_MODEL`, same pattern as the page router's `DEFAULT_ROUTER_MODEL`; overridable via `OPENROUTER_OCR_DISCOVERY_MODEL`), with a 4,000-token completion cap and no reasoning budget at all — discovery only ever names units and groups pages, it was never the room-by-room task that needs Sonnet or a large reasoning budget.
3. **Fan-out deduped by page set, not unit count.** `expandFloorPlanScope` now clusters discovered units by their exact page-number set before creating scopes: a page set used by exactly one unit still gets the tight, name-pinned `unit_variant` scope (unchanged behavior); a page set shared by several units gets **one** `floor_plans`-kind call covering all of them, reusing the multi-unit array parsing already built and tested for the "unmatched pages" fallback path — so a shared page's image is uploaded and billed once regardless of how many units discovery found on it, and each call's output stays bounded to that page's own small cluster rather than the whole scope.

**Why this is not "make the discovery call bigger to compensate."** The 2026-09-02 fix and this one are the same lesson: the fix belongs in the prompt (telling the model what counts as one variant), not in the request-shaping code working around a model that wasn't told. Deduping the fan-out (fix 3) is real defense either way — even a brochure with genuinely 17 distinct units sharing pages should not re-pay for the same page image 5 times — but rule 10 (fix 1) is why the fan-out should rarely be that large in the first place.

**Standing rule this entry adds:** a floor-plan prompt change (`createScopePrompt`'s `variantInstruction`, `createFloorPlanDiscoveryPrompt`, or any future replacement) must check this entry and the 2026-09-02 one before shipping, specifically for whether the mirrored/repeated-unit merge rule survived the change. This has now been lost twice; a third silent drop is not a new bug; it's not reading this file.

**Not yet done:** the Godrej job's existing checkpoint (`.local/ocr-checkpoints/04098e3b-....json`) holds a discovery response and 9 per-unit responses produced under the old, un-deduped prompt — reusing it as-is on retry would keep the old fragmented unit list and defeat this fix. Resetting it, and re-queueing under the new pipeline, is held for the owner's go-ahead as another paid run, per the standing rule.

**2026-09-23 — Root cause of every `output_length` failure and 55% of all extraction spend: `reasoning.exclude` bills for thinking it hides, and its `max_tokens` cap is a parameter Sonnet 5 removed. Reasoning is now disabled outright, the output cap is raised to real headroom, and the two-pass floor-plan split is reverted — it was built to work around a problem that never existed. Supersedes both 2026-09-23 entries above.**

Context: the owner stopped a third Godrej run after ~$2.3 had gone into one brochure's floor plans. Measured against `ai_usage_events` and OpenRouter's pricing endpoint (Sonnet 5 = $2/M input, $10/M output, both confirmed exactly — `76124 × $2/M + 32000 × $10/M = $0.472248`, the recorded cost of the failed call to the cent):

**`reasoning: { max_tokens: 2_048, exclude: true }` was doing the opposite of what it reads like.** `exclude: true` means "generate the reasoning, just don't return it to me" — the tokens are still produced and still billed at the output rate. The `max_tokens` beside it maps to Anthropic's `thinking.budget_tokens`, **a parameter that is removed on Claude Sonnet 5**, so the 2,048 cap was silently ignored on every call. The result, across every brochure this pipeline has ever processed: **$1.85 of $3.35 total spend — 55.2% — bought invisible thinking that was thrown away.** Per-scope, reasoning was 60–84% of output tokens; on the two calls that failed, it was 100% (31,990 of 32,000 on 2026-09-22; 32,000 of 32,000 on the 2026-09-23 retry), which is why they returned `content: null`.

**So `output_length` was never an output-size problem.** `DEFAULT_MAX_COMPLETION_TOKENS` was 32,000; Sonnet 5's actual ceiling is **128,000** (OpenRouter `max_completion_tokens`). Uncapped hidden thinking filled our own self-imposed 32,000 before a single byte of JSON was written. The 2026-09-02 investigation diagnosed this correctly at the time ("spent the output allowance reasoning through the pages rather than producing the required JSON") and prescribed the right fix — "explicitly disabling reasoning or capping it to a small, documented token budget" — but the cap that was then implemented is the one that does not work on this model, and nobody re-measured `reasoning_tokens` afterward to notice. Finding 11 of that tasklist even records the cap being applied and the failure repeating anyway; it was read as a prompt problem instead.

**What this reverses.** The 2026-09-23 two-pass design (a discovery call, then one bounded extraction call per discovered unit) was built to bound output that was never the constraint. It cost an extra full read of every floor-plan page (~$0.152/brochure) purely to produce a page→unit map, and it broke the cross-page merge the 2026-09-02 decision exists to protect: a unit repeated on another floor (Godrej's flat 201 is dimension-for-dimension flat 101) can only be merged by a model that sees both pages in one request. Reverted to one call per `floor_plans` scope, all confirmed pages together, as before.

**Also reverted: discovery on a cheap model.** Swapping that call to `google/gemini-2.5-flash` produced page titles ("GROUND FLOOR PLAN", "1ST FLOOR PLAN") in place of sellable units, which looked like a model-capability gap and is not one: OpenRouter's `file-parser` `engine: "native"` gave Gemini **no page images at all** — that call billed $0.0017 on ~517 tokens for nine dense pages, where Anthropic's native PDF path charges ~8,400 tokens _per page_. It answered from the text layer, and page titles were the only text on those pages. **Standing check: after any model swap on a PDF-reading call, compare `native_tokens_prompt` against ~8,400/page. A cheap number means the model never saw the drawings, and its answer is about the text layer, not the brochure.**

**Changes (`src/lib/ocr/adapter.ts`):** `reasoning: { enabled: false }` (Sonnet 5 accepts `thinking: {type: "disabled"}`; `enabled: false` is OpenRouter's spelling of it); `DEFAULT_MAX_COMPLETION_TOKENS` 32,000 → 64,000 as headroom, not budget — an unemitted token is free, so a low cap buys nothing but failed runs; `expandFloorPlanScope`, the discovery prompt/parser, the per-unit and per-cluster fan-out, the `discoveryModel` option and `maxReasoningTokens` all removed. Kept from the reverted work: the mirrored/repeated-unit merge rule (independently correct, and the reason unit counts stay small), and `effectiveManifest` on `OcrProviderExtractionResult` with `ingestion.ts` resolving `scopeKey` against it — that fixed a real persistence-time silent-drop bug unrelated to any of this.

**Measured projection per brochure**, from real token counts with reasoning removed: router $0.008 + project-details $0.017 + amenities $0.014 + specifications $0.018 + floor-plans ($0.152 input for nine pages, output ≈ units × 2,266 tokens) = **$0.39 at 8 unit types, $0.48 at 12, $0.59 at 17** — against roughly $0.45/brochure before any of this. Godrej is the heavy end (nine dense floor-plan pages); it also carries four pages (2nd basement, 1st basement, layout, terrace) that a human confirmed as floor plans but that hold no sellable unit, ~$0.068/run of input for nothing — a routing choice for the admin, not something extraction should second-guess.

Alternatives considered: keep the two-pass split as insurance against a genuinely oversized brochure — rejected, it costs $0.152 every run to insure against a case that needs >64,000 tokens of pure JSON (roughly 28 full unit types), and that case now fails loudly with a clear re-routing instruction instead of silently; cap reasoning lower rather than disable it — rejected, the cap is the exact thing that does not work on this model, and extraction is transcription against an explicit field contract, not a task that needs chain-of-thought.

## Adopt now — zero new extraction, pure computation from fields already in schema

- **Land area** as its own row (`properties.plotAreaSqft`, already stored, never rendered).
- **Unit density** (units per acre) = `totalUnits / (plotAreaSqft / 43,560)`.
- **Units per floor** (project-level) = sum of `unit_variants[].unitsPerFloor` across a property's variants, when every variant states it.
- **Efficiency** (carpet ÷ super-built-up, as a %) — direct, now that schema v12's duplicate-basis fix means a unit type reliably carries both bases (verified today: 13/13 Godrej Altus variants have both).
- **Balcony area ratio** — balcony room area ÷ unit's own total area, from the room dimensions already captured (`dimensions.balconies`).
- **Amenity category sub-headers.** `amenity_catalog.category` is already loaded into every comparison row (`model.ts` line ~688) and used only to _sort_ — never to render a category heading. Propsoch's Sports / Lifestyle / Neighbourhood grouping is a rendering change against data we already have, not a new field.
- **Developer completed-projects count** — countable from our own `properties` table (developer's properties at `possession_status = ready_to_move`), not a fact to extract.
- **Largest bedroom is arguably already "Master Bedroom Area."** Principle 8 already sorts bedrooms largest-first; Propsoch's row may just be a label on the same fact we already surface. Worth confirming intent before adding a new field for it.

## Needs new fields — design, then extraction, no schema migration expected (the `specification_text` pattern from today covers scalars; only a _numeric_ one needs its own data type)

- **Open area %**, **park area**, **floor area ratio** — need a numeric open-space/built-up figure; today's `specifications.open_space` is free text, not a number a formula can use.
- **Elevator count → elevator crowd factor** — `specifications.lifts_per_tower` is a descriptive sentence ("3 nos. of lifts each in Tower 1, 2, 3 & 4"), not a count. A genuinely numeric field needs its own extraction contract and probably its own data type (`positive_integer`-like) rather than reusing `specification_text`.
- **Clubhouse area, numeric** — `specifications.clubhouse_size` (schema v1) and its wider `amenities_full_list` cousin (v12, today) are both text. A "clubhouse factor" (sqft ÷ units) formula needs a number.
- **Common walls %** — not captured in any form today.
- **Developer established year** — `developers` has no such column; a small additive one if adopted.

## A structural weakness in what shipped today, named honestly

Propsoch's Connectivity rows (Closest Metro, Airport, Hospital, Mall, School) are **discrete, numeric, per-category** — one named place plus one distance per row, letting the UI bar/color/"closer" them directly, exactly what comparison principle 6 asks for. Schema v12's `nearby_connectivity` / `nearby_hospitals` / `nearby_schools` (this session, above) are **flattened text blobs** — dossier-adequate, but comparison cannot do numeric comparison, bars, or "which is closer" on a sentence. Reusing `specification_text` was the safe, no-migration call for getting brochure-read facts into the database at all; it was not designed as comparison's ideal shape. A follow-up — `nearest_metro_distance_km` + `nearest_metro_name`, one pair per category — would need its own small schema entry (still no migration: numeric + text pair, same `property_schema_fields`-driven pattern) and its own comparison rows with real bars.

## New feature ideas, not decided, bigger than a row addition

- **"Common amenities" as its own shown-but-grouped bucket**, ahead of the differing ones. Distinct from the "hide identical rows" toggle already built and removed 2026-09-20 (owner direction: real properties differ on nearly everything, so hiding hid nothing) — Propsoch's version still _shows_ the shared amenities, just groups them first. Worth a real design pass, not an automatic yes.
- **"(Rare)" amenity tagging** — needs a cross-catalog frequency signal (how many published properties have this amenity, recomputed periodically), a new kind of derived data this project doesn't have yet.
- **Neighbourhood natural-feature proximity** (lake, forest, hill, golf course) — a genuinely new fact category, structurally separate from building amenities; not discussed before this review.

## Explicitly rejected, reaffirming standing principles rather than reopening them

- **Propscore (4.14/5 vs 3.79/5)** — a proprietary composite rating. Comparison principle 7: "No score, no rank, no 'winner'." Direct conflict.
- **Price, price on saleable/carpet area** — shown prominently on every Propsoch screen. Comparison principle 7: "No price, price per sq ft or budget bucket, ever." Direct conflict; price never leaves `private` except through the one matching path (`AGENTS.md`).
- **"Investment Potential: Medium/High", "Price Range: Moderate", "Livability: Developing"** — unverifiable subjective labels; "Price Range" is a disguised price signal by another name. Same disposition as the 2026-08-31 precedent on unbuildable pitch-deck asks and the 2026-09-23 investor-metrics chat review (buyer-facing scores rejected there too).
- **The bottom-of-page generated narrative** ("Lodha Mirabelle vs Assetz Soho and Sky... Assetz Soho and Sky has the edge") — reads a winner into cost-efficiency and possession timing. Comparison principle 3 already builds a rule-based "if you choose A over B" summary from verified facts, explicitly "never generated text, never a score" — the mechanism we want already exists; Propsoch's version is the score-laundering pattern principle 3 was written to avoid.
